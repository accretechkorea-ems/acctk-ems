# 운영 — 오류 모니터링(Sentry)

지금까지 운영에서 오류가 나면 **아무도 몰랐다.** 사용자가 전화할 때까지 몰랐고, Vercel 함수
로그는 사람이 열어 봐야 보였다. Sentry 를 붙여 그 구멍만 메웠다.

**코드는 이미 들어가 있다.** 남은 일은 Kevin 이 ① Sentry 계정에서 프로젝트를 만들고
② Vercel 에 환경변수 두 개를 넣고 ③ 알림을 켜는 것이다. 아래 순서대로 하면 된다.

---

## 0. 지금 상태 — DSN 이 없으면 꺼져 있다

환경변수를 넣지 않으면 Sentry 는 **아무것도 하지 않는다**(초기화조차 하지 않는다).
그래서 로컬·CI 는 키 없이 그대로 돌아간다. 넣는 순간 켜진다 — 배포가 다시 필요하다.

---

## 1. Sentry 프로젝트 만들기 (5분)

1. <https://sentry.io> → 가입(개인 계정이면 **Developer** 요금제가 무료다).
2. **Create Project** → 플랫폼 **Next.js** → 프로젝트 이름 `acctk-ems`.
3. 안내 화면에 **DSN** 이 나온다. `https://<키>@o<숫자>.ingest.us.sentry.io/<숫자>` 꼴이다.
   이 값을 복사한다. **설치 안내(마법사 실행)는 따라 하지 않는다 — 코드는 이미 들어가 있다.**

> DSN 은 비밀이 아니다(브라우저로 나간다). 다만 아무 데나 적어 두지는 말자 — 남이 알면
> 우리 프로젝트로 쓰레기 이벤트를 보낼 수 있다.

---

## 2. Vercel 에 환경변수 두 개

Vercel → 프로젝트 → **Settings → Environment Variables** 에서 **Production·Preview** 둘 다에 넣는다.

| 이름 | 값 | 쓰는 쪽 |
|---|---|---|
| `SENTRY_DSN` | 1번에서 복사한 DSN | **서버**(라우트·서버 컴포넌트) |
| `NEXT_PUBLIC_SENTRY_DSN` | 같은 DSN | **브라우저**(화면) |

- 두 개를 **같은 값**으로 넣는다. 이름이 둘인 이유는 `NEXT_PUBLIC_` 이 붙은 것만 브라우저
  번들에 들어가기 때문이다(서버 전용 값을 브라우저로 내보내지 않는 규칙).
- 넣은 뒤 **Redeploy** 해야 적용된다(환경변수는 빌드할 때 번들에 박힌다).
- 로컬에서도 켜 보고 싶으면 `.env.local` 에 같은 두 줄을 넣는다. **평소에는 넣지 않는다** —
  개발 중의 오류까지 쿼터를 먹는다.

---

## 3. 동작 확인 — 일부러 오류를 내 본다

배포가 끝난 뒤:

1. **서버 쪽** — 브라우저 주소창에 로그인한 상태로 이것을 넣는다.
   ```
   https://<우리 주소>/api/device-image?path=
   ```
   `400`(`path required`)이 돌아온다. **이건 Sentry 에 안 온다** — 라우트가 제대로 다룬
   오류이기 때문이다. 그게 정상이다.

   일부러 **미처리 예외**를 내려면 없는 라우트를 부른다.
   ```
   https://<우리 주소>/api/없는라우트
   ```
   404 는 예외가 아니라 역시 안 온다. **확실한 방법은 한 번만 쓰는 시험 라우트**다 —
   필요하면 말해 주면 `app/api/sentry-test/route.ts`(일부러 throw)를 만들어 주고,
   확인한 뒤 바로 지운다. 그 편이 운영 코드에 시험용 길을 남기지 않는다.

2. **브라우저 쪽** — 어느 화면에서든 개발자 도구(F12) 콘솔에 이것을 넣는다.
   ```js
   setTimeout(() => { throw new Error('Sentry 확인 — 무시하세요') }, 0)
   ```
   1분 안에 Sentry **Issues** 에 `Sentry 확인 — 무시하세요` 가 뜨면 성공이다.
   (`setTimeout` 으로 감싸는 이유 — 콘솔에서 바로 throw 하면 브라우저가 콘솔 오류로만
   처리하고 전역 핸들러까지 가지 않는 경우가 있다.)

3. 뜬 이슈를 눌러 **무엇이 적혀 있는지** 확인한다. 이렇게 보여야 한다.
   - `user` 에 **id(사번) 하나만** 있다 — 이름·메일이 없다.
   - `request` 에 **주소와 메서드만** 있다 — 본문·헤더·쿠키·질의 문자열이 없다.
   - 스택이 압축된 글자(`a.b.c`)로 보인다 — 소스맵을 올리지 않기 때문이다(아래 5번).

   하나라도 다르면 **멈추고 알려 달라.** 보내면 안 되는 것이 나가고 있다는 뜻이다.

---

## 4. 알림 켜기 — 메일로 받기

Sentry 는 기본으로 메일을 보내지만, 쓸 만하게 하려면 두 가지를 손대는 것이 좋다.

### 새 이슈가 생기면 바로 메일

1. 프로젝트 → **Settings → Alerts**(또는 왼쪽 **Alerts** → **Create Alert**)
2. **Issues** 종류를 고른다 → 조건을 **「A new issue is created」** 하나만 둔다.
   («이슈가 다시 났을 때»까지 켜면 같은 오류로 메일이 계속 온다.)
3. 받는 사람 — **Team** 또는 본인 메일. **Environment** 는 `production` 으로 좁힌다
   (Preview 배포의 오류까지 메일로 받으면 금방 무시하게 된다).
4. Save.

### 주간 요약

개인 계정 설정에서 켠다 — 오른쪽 위 아바타 → **User settings → Notifications** →
**Weekly reports** 를 켜 둔다. 월요일 아침에 「지난주 무엇이 몇 번 터졌나」가 한 통 온다.

### 조용히 하기

필요 없는 오류가 계속 오면 그 이슈 화면에서 **Ignore**(또는 **Archive**)를 누른다.
같은 종류가 다시 와도 메일이 오지 않는다. 지우는 것(Delete)보다 이게 낫다 —
횟수는 계속 세어 준다.

## 5. 쿼터와 한계 — 알고 있어야 하는 것

| | |
|---|---|
| **무료 쿼터** | 오류 **월 5,000건**. 넘으면 그 달의 나머지는 **버려진다**(요금이 붙지 않는다). |
| 보내는 것 | 서버 라우트의 **미처리 예외** · 브라우저의 **미처리 예외**. 이 둘뿐이다. |
| 보내지 않는 것 | `console.error`(코드에 658곳 있다) · 라우트가 제대로 다룬 400·500 · 성능 추적(traces 0). |
| 소스맵 | **올리지 않는다.** 올리려면 Sentry 인증 토큰을 Vercel 에 넣고 빌드마다 업로드해야 하는데, 토큰 관리가 늘어난다. 그래서 스택이 압축돼 보이는 것을 감수한다 — 어느 라우트·어느 화면인지는 그래도 보인다. |
| 사용자 | **사번(engineer_id)만.** 이름·메일은 보내지 않는다. 누구인지 알아야 하면 사번으로 직원 관리에서 찾는다. |

쿼터가 자꾸 찬다면 그것 자체가 신호다 — 무엇이 많이 터지는지 보고 그 오류를 고치는 쪽이
맞다. 설정으로 줄이는 것은 그다음이다.

---

## 6. 되돌리기

환경변수 두 개를 **지우고 Redeploy** 하면 완전히 꺼진다(코드를 되돌릴 필요가 없다).
다시 켜려면 값을 넣고 Redeploy 한다.

## 코드가 어디 있나

| 파일 | 하는 일 |
|---|---|
| `lib/sentryOptions.ts` | DSN 읽기 · **보내기 전 지우는 규칙**(scrubEvent) · 샘플링 값 |
| `instrumentation.ts` | 서버·엣지 초기화 + `onRequestError`(미처리 예외) |
| `instrumentation-client.ts` | 브라우저 초기화 |
| `app/global-error.tsx` | React 가 그리다 터졌을 때 — 기록하고 「다시 시도」를 보여 준다 |
| `lib/appData/me.ts` | 로그인한 사람의 **사번만** 적는다 |
| `next.config.ts` | CSP `connect-src` 에 `*.ingest.sentry.io` — **없으면 보고가 조용히 막힌다** |
| `scripts/sentry-scrub-check.js` | 보내면 안 되는 것이 섞이지 않는지 시험(27건) |
