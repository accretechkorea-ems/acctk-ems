## 조사 방법과 한계

**방법** — `app`·`lib`·`components`·`hooks`·`db`·`scripts` 전체를 대상으로 상수 선언(`as const`·`export const`), 회사 정보 글자,
메일·PDF 문구, 환경변수(`process.env`), 숫자 리터럴, 스위치(`HIDE_*`·`*_ENABLED`)를 검색해 모았다.
DB 는 service role 로 **표 존재 여부와 줄 수만** 읽었다.

**한계(사실)**

1. **DB 안의 함수·RLS 정책은 전부 보지 못했다.** 레포의 `db/` 에는 적용한 SQL 일부만 있다(`db/APPLIED.md`).
   견적번호를 만드는 `create_quote`·`next_quote_seq`, 권한을 판정하는 `has_team_perm`·`has_menu_perm` 처럼
   **운영 규칙이 DB 함수 안에 있는 것**이 더 있을 수 있다 — 전수하려면 `pg_proc` 조회가 필요하다(이번 범위 밖).
2. 「누가 바꾸고 싶어 하나」와 「빈도」는 **전부 추측**이다. 접근 로그가 없어 카드별 실제 사용량은 재지 못했다
   (추정 근거는 코드 참조 수와 데이터 줄 수뿐).
3. RLS 가 화면 권한 구멍(문제 4)을 실제로 막는지는 확인하지 않았다.
4. 토스트·알림 문구(I3, 120곳)는 개별 행으로 세지 않고 묶음 하나로 셌다.
