# EMS 전수조사 — 코드 구조·운영 체계 (2026-10-23)

조사만 했다. **코드·DB·설정은 한 줄도 바꾸지 않았다.** DB 는 읽기(select·OpenAPI 문서·
읽기 전용 함수 호출)로만 확인했고, 자격·고객 자료 값은 이 문서에 적지 않았다.

규모: 소스 402개 파일 · 91,010줄(app·components·lib·hooks·scripts) · API 라우트 53개 ·
표·뷰 62개 · DB 함수 19개 · 버킷 12개(599파일 160MB) · 커밋 409개(최근 30일 225개).

---

## 0. 요약 — 상위 10개

순서는 「먼저 할 것」이다. 운영 체계가 코드 정리보다 앞에 있다 — 지금 깨지면 되돌릴 방법이
없는 것이 먼저다.

| # | 무엇 | 이득 | 비용 | 위험 |
|---|---|---|---|---|
| 1 | **스토리지 백업이 없다** — 버킷 12개 599파일 160MB 가 Supabase 일일 백업(7일) 밖에 있다 | 견적 PDF·납입의사록·의뢰서 첨부가 지워지면 되돌릴 수 있다 | 주 1회 스크립트 + 보관 장소 1곳 (반일) | 지금은 실수로 지우면 **복구 불가**. 받는 쪽이 「원본 주세요」 하면 끝 |

**(가) 번호 매긴 폴더 + 적용 기록 표** (도구 없이, 반일)

**주 1회 백업 스크립트 초안**(실행하지 않았다 — 초안이다)

```bash
# scripts/backup/weekly.sh   — 매주 월요일, 로컬 PC 또는 사내 NAS 에서 돈다
set -euo pipefail
DEST="${BACKUP_DIR:?BACKUP_DIR 를 정해라}"       # 예: D:/ems-backup  또는  //nas/ems
STAMP=$(date +%Y%m%d)
OUT="$DEST/$STAMP"; mkdir -p "$OUT"

# ① DB — 역할·소유자 없이 자료만(복구할 때 권한 충돌이 없다)
pg_dump "$SUPABASE_DB_URL" --no-owner --no-privileges -Fc -f "$OUT/db.dump"

# ② 스토리지 — 버킷마다 통째로. supabase CLI 가 재귀 복사를 해 준다
for B in packing-lists inquiry-attachments device-images service-report quote-pdfs \
         service-attachments purchase_orders showroom-approvals profile-images \
         lead-cards notices suggestion-images; do
  npx supabase storage cp -r "ss:///$B" "$OUT/storage/$B" --experimental
done

# ③ 저장소 상태 — 그때의 코드와 스키마 파일
git -C "$EMS_REPO" bundle create "$OUT/repo.bundle" --all

# ④ 오래된 것 정리 — 8주치만 남긴다
ls -1d "$DEST"/20* | sort | head -n -8 | xargs -r rm -rf
echo "끝: $OUT  ($(du -sh "$OUT" | cut -f1))"
```

**어디에 두면 Kevin 없이도 복구 가능한가** — 세 가지를 **동시에** 만족해야 한다.

1. **두 곳 이상** — 사내 NAS(또는 담당 PC의 고정 폴더) + 클라우드 드라이브(회사 Google Drive/OneDrive) 사본.
   한 곳만 두면 그 PC 가 고장날 때 같이 간다.
2. **열쇠가 백업 안에 없어야 한다** — `pg_dump` 에 쓰는 접속 문자열과 service role 키는 백업에
